# Architecture

The build contract. `docs/spec.md` is the product intent; this file is how we build it. Research behind every integration decision is in `docs/research/`. When this file and a research doc disagree, this file wins; when this file and real package behavior disagree, fix this file.

Product name: **Morrow** (one constant, `APP_NAME`, in `packages/contracts`).

House rules: Bun everywhere. No git in this folder, no commits. No dates or timestamps in any doc. Never call bare `node` in shells on this Mac (use `~/.nvm/versions/node/v22.21.1/bin/node`); Bun is `~/.bun/bin/bun`.

---

## 1. Runtime topology

```
Browser ──https──> web (Next.js 16, :3000)
   │                 └─ rewrites /api/* ──> backend (Bun + Hono, :8787)
   │                                          ├─ Terse dev server (127.0.0.1:7100, durable-actors dev --no-watch)
   └──wss (ticket)──> backend /realtime       ├─ Agent Relay (hosted cast.agentrelay.com, or self-hosted engine)
                                              ├─ Freestyle API (VMs, PTY, files)
                                              └─ GitHub API (OAuth, repos, refs, PRs)

Freestyle VM (one per engineer environment)
   ├─ Linux user per engineer (CLI logins live in that $HOME)
   ├─ agent-relay node (systemd, runs as that user, outbound WSS only)
   └─ git worktrees under /home/<user>/work/<repo>/<branch>
```

- Only the backend talks to Terse, Relay, Freestyle and GitHub. The browser never holds a vendor credential, with one deliberate exception: a short-lived Freestyle identity token for the VM owner's own private terminal (section 8.4).
- Same-origin REST: Next.js rewrites `/api/*` to the backend, so the session cookie is first-party.
- Realtime does not go through Next.js. The browser asks `/api/realtime/ticket` for a 30 s single-use ticket, then opens `wss://<REALTIME_URL>/realtime?ticket=...` on the backend directly.

## 3. Spec corrections we adopt

| Spec | Change | Why |
|---|---|---|
| `TeamWorkforce(teamProjectId)` | `TeamWorkforce(teamId)`. Tasks carry `projectId`. | A CLIProfile is shared by all projects of a team. Per-project actors could lease the same profile twice. The lease authority must own the whole profile pool. |
| Worker monitor emits signed events from VMs | Monitor runs in the backend: Relay observer (agent/node lifecycle) + Freestyle state polling + reading Relay worker logs with `vm/logtail.sh` exec'd as the engineer + periodic `vm.exec` probes. No `/api/events/worker`. | No secret on VMs that agents could read; nothing extra to deploy. Logs need a running VM; only live leases are read. |
| `onAlarm` drives cooldowns/retries | Deadlines live in persisted state. Backend calls `reconcile()` on boot and every 15 s. The alarm is only an early wake-up. | Local Terse loses pending alarms on restart; alarms are outside `@Atomic`. |
| "Do not indiscriminately use @Interleave" | No `@Interleave` in any actor. Every state transition is `@Atomic`. | One interleaved method disables rollback for the whole class. Plain methods keep partial writes. |
| Relay node "enroll" step | `agent-relay node up --broker-name <node>` with `RELAY_WORKSPACE_KEY`; it registers itself. | Verified in source and live. |
| Agent identity `agent-<taskShort>-<role>@<node>` | Name `w-<taskShort>-<role>-e<epoch>`; Relay supplies `@<node>`. | Names are workspace-wide, cannot reuse node names, released names stay taken unless deleted. Epoch makes every lease's name unique. |
| `vm.exec` max 5 min | Default is 30 s. Always pass `timeoutMs`. Long work runs in Relay-spawned PTYs. | SDK types. |
| "Install Relay + Git in a pre-login snapshot" | Git is preinstalled. Golden snapshot installs Relay only, never runs `node up`, nothing logged in. | Snapshots copy memory + disk; node identity and credentials would clone. |
| Codex login | `codex login --device-auth` in the terminal. | Default flow needs a localhost callback the browser cannot reach. |
| PTY shell | Open with `env TERM=xterm-256color bash -l`. | Claude TUI exits without TERM. |
| Relay spawn status | Never a single signal. Reconcile with node `relay:live-agents:v1` + `agent.exited`. | Observed false failures live. |

## 4. Identity, sessions, authorization

- **Login:** GitHub OAuth App, scopes `read:user user:email repo`. Flow: `GET /api/auth/github` sets a signed `oauth_state` cookie (random 32 B, 10 min, httpOnly, SameSite=Lax) and redirects; callback verifies state, exchanges code, fetches the GitHub user, upserts the `User` actor (`u-<githubId>`), stores the GitHub token encrypted.
- **Session:** stateless encrypted cookie `morrow_session` (AES-256-GCM via WebCrypto, key from `SESSION_SECRET`): `{ uid, sv, exp }`. httpOnly, Secure in production, SameSite=Lax, 14-day max age, sliding refresh when under half life. `sv` (session version) lives in the User actor; logout-everywhere bumps it, closes the user's realtime and inspect sockets, burns their unused tickets and cuts every terminal grant and token they hold (section 8.4). Every request checks `sv` (cached 30 s in memory).
- **CSRF:** mutating requests must send header `x-morrow-csrf: 1` and an `Origin` equal to `APP_ORIGIN`. SameSite=Lax plus the custom header blocks cross-site form posts.
- **Authorization:** every team route loads membership from the Team actor. Roles: `owner`, `admin`, `member`. Resource rules:
  - Team settings (rename, policy), invites, removing members: owner/admin. Changing a member's role (admin/member): owner only. The owner's own role never changes and there is no ownership transfer.
  - Environments (VMs) and CLIProfiles: the owning user manages; admins can pause/disconnect.
  - Private terminal: only the environment owner. Read-only inspect of a worker's session: any member, only while that worker has a live lease on a task in this team (policy flag per team, default on).
  - Tasks: any member creates/starts/messages; cancel by creator or admin.
- **Invites:** owner/admin creates an invite: random 32 B code, stored as SHA-256 hash with expiry (7 days) and max uses (default 1, up to 50). Link `/join/<teamId>.<code>`. Accept and preview look the hash up by key. Each invite also has a public id (`inv-...`) used to list and revoke it; the code and hash never leave the actor. A removed member cannot come back through an invite made before the removal; a fresh invite works.
- **Signup allowlist:** optional `SIGNUP_ALLOWLIST` (comma-separated GitHub logins). When set, everyone else lands on `/login?error=not_allowed` and no user record is created. Checked at sign-in only, so rotate `SESSION_SECRET` when turning it on.
- **Per-user caps:** at most 5 owned teams and 3 live environments across all teams, checked under a per-user lock (single backend instance).
- **Rate limits:** in-memory token bucket per route group (auth, mutations, terminal tokens), keyed by user, or by client IP before sign-in. The client IP is the socket peer unless `TRUSTED_PROXY_HOPS` (0 to 5, default 0) says how many proxies in front append to `X-Forwarded-For`; the entry that many places from the right is used, so a client cannot pick its own bucket. Single backend instance for now; note in section 13.
- **Member removal:** the member's realtime and inspect sockets close; their environments in that team are disconnected (terminal identity deleted, grants revoked, VM deleted, profiles removed so live leases expire into handoff from the last pushed checkpoint; work after it is dropped, never pushed); the observer token rotates; their Relay `h-<login>` identity is revoked. The reconcile loop disconnects any environment whose owner is no longer a member, so a crash mid-cleanup is retried.

## 5. Terse actors

Shared rules (from `docs/research/terse.md` section 8): extend `Actor` directly; every transition `@Atomic`; no `@Interleave`; reassign persisted objects, never mutate in place; helpers are `#private` or module functions; validate every argument (zod) at the top of each method; no network I/O; idempotency ledger pruned to the last 500 (in state for Team, in SQLite for TeamWorkforce); IDs match `[A-Za-z0-9._-]{1,128}`.

Sockets: actor sockets are backend-only. `onConnect` rejects (4003) any socket whose metadata is not `{ userId: "system.backend" }`; browsers get actor state through the backend hub, after its membership checks (section 7). Accepted sockets get a gateway auto-response (`{"type":"ping"}` answered with `{"type":"pong"}`) so the backend's 25 s keepalive need not wake an actor. The pinned runtime (durable-actors 0.14.4) answers at the gateway, so actors have no `onMessage`; `the keepalive ping gets the gateway's pong` in actors/test/workforce.integration.test.ts asserts the exact reply, and fails if a runtime stops answering. (0.14.3 did not answer.)

### 5.1 `User` (id `u-<githubId>`)
Persisted: `profile { githubId, login, name, avatarUrl, email }`, `githubTokenEnc` (backend-encrypted blob, never decrypted in the actor), `sessionVersion`, `teamIds[]`, `relayHumanTokens { [teamId]: enc }`.
Methods: `upsertFromGithub`, `get`, `bumpSessionVersion`, `addTeam`, `removeTeam`, `setRelayHumanToken`.

### 5.2 `Team` (id `t-<rand>`)
Persisted: `info { name, slug }`, `members { [userId]: { role, joinedAt } }`, `invites { [hash]: { id, createdBy, createdAt, expiresAt, uses, maxUses } }`, `removed { [userId]: removedAt }`, `projects { [projectId]: { repoFullName, repoId, defaultBranch, createdBy } }`, `environments { [envId]: Environment }`, `relay { workspaceId, baseUrl, workspaceKeyEnc, dispatcherTokenEnc, observerTokenEnc, observerTokenId, cursor }`, `policy { allowInspect, maxParallelPerTask }`, `processed` ledger.
`Environment { id, ownerUserId, freestyleVmId, freestyleIdentityId, linuxUser, nodeName, phase, vmState, nodeOnline, lastError, createdAt }` (Freestyle ids are backend-only, never in the team view) with `phase: provisioning | bootstrapping | awaiting_login | ready | paused | error | disconnected`.
`@Emittable`: one field, `view`, a secret-free projection of `info`, `members`, `projects`, `environments`, relay readiness and `policy` (`buildTeamView`), reassigned only when it changes. Secrets are in private fields only.

### 5.3 `TeamWorkforce` (id = teamId)
The lease authority and task state machine. The view is emitted in three parts, `profilesView`, `tasksView` and `leasesView`, each reassigned only when it changed, so a checkpoint resends the tasks, not the profiles. The backend composes them into `{ profiles, tasks, leases }` (`backend/src/actors/workforceState.ts`); the browser's `workforce.view` frame is byte-for-byte what it was with one field. A fourth emitted field, `outboxSummary { open, nextDueAt }`, tells the backend when the next outbox item is due, so it claims on push instead of polling (section 9.2). The ledger and the outbox stay private.

Storage (schema 2, `actors/src/lib/store.ts`). Records live in the actor's SQLite, written by diff, inside the method's transaction (`@Atomic` rolls rows and fields back together; a failed call also rebuilds the instance, so the in-memory copy cannot outlive a rollback): `wf_profile`, `wf_lease`, `wf_outbox` (one JSON row each), `wf_task` plus `wf_task_field` (one row per top-level field) and `wf_task_item` (trace, checkpoints and workstreams, one row per entry), and `wf_ledger`. Schema 1 kept each record map in one `@Persisted` field, and the runtime rewrites a changed field whole: at the caps (`actors/test/store-budget.test.ts`) one checkpoint rewrote 847 MB in the worst case and 42.7 MB in a realistic one, against 96 KB and 9 KB now; a claim rewrote 22 MB (1.3 MB realistic) against 0.4 KB. `@Persisted schemaVersion` (0 when absent) drives the upgrade: the first call of any kind, a socket connect included, copies the schema 1 fields into SQLite before any method logic runs, and a later call empties them (`actors/test/upgrade.integration.test.ts` loads real schema 1 data and checks every record, the ledger and the watermarks).
Every call still loads all `@Persisted` fields twice (the runtime diffs emitted state), and those are now the emitted parts plus small fields. The in-memory copy of the records is still the whole state; at the stored-task cap with every field at its limit that passes the default 256 MiB actor memory, so `storedTasks` or archiving finished tasks out of memory is the next lever if real teams get near it.
The view parts are resent on every change, so their size must not grow with a task's age, and must stay well under the hub's 1 MB slow-consumer limit:
- A task in the view (`TaskView`) is a summary with no long text: id, project, title, creator, status, `maxAgents`, workstreams as `{ id, branch, status, leaseId }`, the newest trace entry with its message cut to 120 characters (`viewTraceEntries`, `viewTraceMessageChars`), `traceTotal` (entries recorded in all), and times read from the whole stored trace: `runStartedAt` (first reservation after the latest plan), `retriedAt` (latest `task.retried`), `plannedAt` (latest `task.planned`), plus `resolutionAttempts`, `createdAt`, `updatedAt`. `taskView` names each field, so a new field on the stored task never leaks into the view by accident.
- Everything long lives in the task detail (`TaskDetail`): prompt, acceptance, plan (rationale, warnings), workstream role, title, `why`, `dependsOn` and last checkpoint (`WorkstreamDetail`), verification checks, and every stored trace entry (a task keeps its newest 200; `traceCount` counts every one). Browsers read it from `GET .../tasks/:taskId`. `getTask` returns a `TaskRecord`: the detail plus each workstream's `brief` and `ownership`, which only the backend reads (dispatcher, scheduler, handoff note, conflict brief, planner revision, verifier). The route parses it with the `TaskDetail` schema, which drops both. The types make reading any of these from `getView` a compile error.
- A profile's `limitedReason` (text a CLI printed) is cut to the same 120-character preview in the view.
- Size ceiling: `actors/test/view-budget.test.ts` builds the worst case the actor allows: 100 profiles, 100 active plus 20 shown finished tasks, 400 live leases (two thirds of them subagents, which carry `parentLeaseId`) and 300 ended ones, every user-, planner- and agent-written field at its validation limit in three-byte characters, six workstreams per task, ids and names at their minted lengths. One task is at most `VIEW_TASK_MAX_BYTES` (2 KB; measured 2.0 KB, against about 1 MB for the same stored task). The whole `workforce.view` frame is 0.69 MB (tasks 0.25, profiles 0.23, leases 0.22); the test fails above 700 KB. Three bytes per character holds because `line`/`text` (actors) and `trimmed` (contracts) reject half a surrogate pair, which JSON would escape to six bytes, and every clip keeps pairs whole.
- Before the summary (50 active plus 20 finished, 3 workstreams, 200 entries each): 3.2 MB with 100-character messages, 8.7 MB at the message maximum, and 2.8 MB more from long prompts, `why` and acceptance.

State:
- `profiles { [profileId]: CLIProfile }`: `{ id, envId, ownerUserId, cli: 'claude'|'codex'|'opencode', label, auth: 'unknown'|'ok'|'auth_required', availability: 'ready'|'busy'|'limited'|'offline', cooldownUntil?, limitedReason?, maxConcurrent (1-8, default 4: workers at once, subagents included), scopes: projectId[] | 'all', lastSeenAt, usage? }`. `usage` is the latest plan-usage reading (`{ windows: [{ kind: five_hour|weekly|other, label, usedPercent 0-100, resetsAt|null }] (max 6), observedAt, source: probe|worker }`, section 8.5), null until the first one.
- `tasks { [taskId]: Task }`: `{ id, projectId, title, prompt, acceptance[], createdBy, mode?, pins?, status, plan?, workstreams[], checkpoints[], verification?, generation, resolutionAttempts?, createdAt, updatedAt }`, `status: draft | planning | planned | starting | running | handoff | verifying | resolving | completed | failed | cancelled`. `resolving` means a worker is resolving a merge conflict (section 9.5).
- `Workstream { id, role, title, brief, why, branch, dependsOn[], ownership[], leaseId?, lastCheckpoint?, status: pending|active|handoff|done|failed }` (the task detail's `WorkstreamDetail` drops `brief` and `ownership`; the view's `WorkstreamView` keeps only `id`, `branch`, `status`, `leaseId`)
- `leases { [leaseId]: Lease }`: `{ id, taskId, workstreamId, profileId, epoch, agentName, nodeName, state: reserved|spawning|running|released|expired|failed, spawnInvocationId?, createdAt, expiresAt }`
- `epoch` (monotonic), `outbox { [id]: OutboxItem }` (`{ id, kind: 'spawn'|'release'|'handoff_brief'|'checkpoint', leaseId, payload, attempts, nextAt, state }`), `processed` ledger.

Methods (all `@Atomic`, all validate input, all idempotent by key where external input):
`registerProfile`, `updateProfileHealth(profileId, health, eventId)`, `removeProfile`, `createTask`, `recordPlan(taskId, plan, key)`, `reserveWorkers(taskId, picks[], key)` (rejects any profile not ready / over capacity / out of scope; issues leases with fresh epochs; enqueues `spawn` outbox items), `claimOutbox(now, limit)` (marks items in-flight with a visibility timeout, returns them), `completeOutbox(id, result, key)`, `recordSpawnStatus(leaseId, epoch, status, invocationId, eventId)`, `reportCheckpoint(taskId, workstreamId, epoch, sha, summary, eventId)`, `recordProfileUsage(profileId, usage)` (monotonic by `observedAt`, section 8.5), `markProfileLimited(profileId, until, reason, source: 'detected'|'manual', eventId)` (cooldown, revoke the profile's running leases to `expired`, set affected workstreams to `handoff`, enqueue replan), `requestHandoff(taskId, workstreamId, fromEpoch, toProfileId, key)`, `ackHandoff(leaseId, epoch, eventId)`, `submitVerification(taskId, evidence, key)`, `resolveConflict(taskId, evidence, conflict, key)` (section 9.5), `cancelTask`, `retryTask(taskId, byUserId, key)` (section 9.5), `reconcile(now)` (restore due cooldowns, expire stale leases, re-arm alarm), `onAlarm()` (calls the same sweep; no-op when nothing due).

Fencing: every external report carries `(leaseId, epoch)` (the lease identifies task and workstream). A report whose epoch is not the workstream's current lease epoch is ignored and returned as `{ ok: false, reason: 'stale_epoch' }`. Completion is accepted only for the current epoch.

As built, also: `beginPlanning` (the planning hold), `completeWorkstream`, read getters, Team invite/project/environment/relay/policy/role methods. Outbox claims hide an item per kind (`spawn`/`handoff_brief` 6 min, `checkpoint` 3 min, `release` 1 min) so a slow honest side effect never burns an attempt; a lease that never starts expires after 10 min. Trace kinds include `task.planning` (names the planner profile) and `task.planner_fallback` (with reason), plus the merge-conflict kinds `task.conflict_detected`, `task.resolver_reserved`, `task.conflict_resolved` and `task.conflict_gave_up` (section 9.5).

Subagents (`docs/subagents.md`): `delegate(input)`, `recordSubagentResult(leaseId, epoch, status, summary, eventId)` and `cancelSubagent(parentLeaseId, childLeaseId, reason)`. A subagent is a lease with `parentLeaseId` and `role` on its parent's task and workstream, on another CLI profile of the parent's own environment and owner (2 live per worker, 4 per task). It owns no workstream: invariants and fencing skip it, it never checkpoints, and it ends with its parent. `Task.subagents` keeps a record per child (newest 20, running ones always kept) and `TaskDetail.subagents` serves it; the view carries only live subagent leases. Trace kinds `subagent.started` and `subagent.finished`.

## 7. Realtime

- One backend WS per browser tab, authenticated by ticket. Server pushes `RealtimeEnvelope { v: 1, teamId, kind, seq?, data }` where `kind` is `workforce.view` (Terse emittable state), `team.view`, `relay.event` (normalized message/thread/DM/lifecycle), `env.status`, `terminal.*` (inspect only), `toast`, `github.changed` (section 8.6).
- Fan-out hub keeps per team: one Terse actor socket per actor (TeamWorkforce, Team) opened by the backend via `prepareWebsocket` and kept alive with reconnect + fresh grant; one Relay observer event source (cursor persisted to `Team.relay.cursor`, flushed every 5 s); Freestyle status poller (every 10 s for environments with subscribers, 60 s otherwise).
- On connect the hub sends current snapshots (last `state` from Terse, recent Relay history page) so the UI never needs a separate fetch to render.
- Screens that show a task's long text fetch its detail (`useTaskDetail`): the plan review card (team home) and mission control (recovery chain, lanes, decision trace, waiting workstreams, Branches and Tests tabs). The first fetch runs at once; after that the hook refetches whenever the live task's `updatedAt` moves, at most once per 1.5 s, so a busy task does not drain the read rate limit, and skips a fetch the last answer already covers. Each section shows a loading row, or an error with Try again (keeping an older copy on screen when it has one). The plan card waits for a detail as new as the live task, so Start never sends picks for an older plan; refine and cancel read the prompt and acceptance from it. Everything else (inbox, Needs you, recent tasks, pool meter, the scheduler's retry budget) reads the summary.
- Browser client reconnects with backoff 0.5 s → 10 s, fetching a new ticket each time.
- Lost logins: when a workforce view moves a profile from `auth: ok` to `auth_required` (probe or monitor), the hub sends a `toast` to that profile owner's sockets on that team only (`publishToUser`, membership-checked against the latest team snapshot). It fires once per transition, never on later probes or a channel's first snapshot. The Workforce nav link counts the viewer's own signed-out CLIs; "Sign in again" opens the owner's private terminal with the CLI's login command typed in, and closing it runs a profile check.

## 8. Integrations

### 8.1 GitHub
OAuth (section 4). Repo list via `GET /user/repos` with the user's token. Verification: `GET /repos/{o}/{r}/commits/{sha}` and `compare` to prove a checkpoint SHA exists on the remote; PR create for integration. Tokens decrypted only in memory for the call.

### 8.2 Freestyle
- Golden snapshot `morrow-base` built by `backend/vm/golden-setup.sh` via `freestyle snapshot create --base freestyle/ubuntu`: installs Agent Relay pinned (`install.sh` with `AGENT_RELAY_VERSION`, telemetry off, no engine), `gh`. Never runs `node up`, never logs in.
- Provisioning state machine (backend, idempotent per envId, persisted in `Team.environments`): `provisioning` (`vms.create` from `morrow-base`, `firewall: allow public egress`, metadata `{ app: morrow, team, env }`, no idle timeout) → `bootstrapping` (create Linux user `u<short>` without sudo; clone linked repos through the root-owned mirror, see "Git and the GitHub token"; save the owner's warm snapshot, see below; then write `/etc/agent-relay/node.env` 0600 root, lay out the node (section 8.3, "Node layout") and write the systemd unit) → `awaiting_login` (user opens private terminal and logs in claude/codex) → `ready` once a profile probe passes.
- **Warm snapshots** (`backend/src/integrations/freestyle/warm.ts`): cloning is most of a cold start (26 to 100 s against a few seconds for everything else). Once an environment's repos are cloned, and before its Relay node is configured, the VM is snapshotted as its owner's warm image: slug `mw-` + a hash of team, owner, golden image id and the sorted repo set; display name `morrow warm <hash of team and owner>`; deleted by Freestyle after 7 days unused. It holds the Linux user, the root-owned mirrors and the checkouts, and nothing else: no `node.env`, no workspace key, no node identity, no CLI login (CLIs rotate refresh tokens, so two VMs from one signed-in image would sign the owner out), and the capture is skipped while any credential file is left in `/var/lib/morrow/cred`. The owner's next environment in that team boots from it only if GitHub still lets the owner read every repo in it (`GET /repos` with the owner's token; any error means the golden image), then runs the normal clone step, which on a warm VM is an incremental fetch. A failed capture is a warning (`warm_snapshot_failed`), never an environment failure. A newer capture deletes the owner's older ones; removing a member deletes theirs. Each one counts against the Freestyle plan's snapshot limit (10 on Free).
- Health probe (`vm/probe.sh`, `exec` as the Linux user, `timeoutMs: 20000`): `claude --version`, `codex --version`, auth heuristics (presence and freshness of `~/.claude/.credentials.json` or `claude auth status` if available; `codex login status`), returns JSON.
- **Git and the GitHub token** (`vm/git.sh`): only root talks to GitHub. Each engineer has a bare mirror per repo at `/var/lib/morrow/mirrors/<user>/<owner>__<name>.git` (root-owned, group-readable by the engineer, never writable). The token is the environment owner's only, never another member's; it reaches the VM as a fresh file `cred.<random>` in `/var/lib/morrow/cred` (0700 root) written over the Freestyle file API and deleted on exit (stale files swept after 15 min), so it is in no environment, argv or engineer-readable file. Root git runs with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, hooks off, fsmonitor off, no proxy, HTTPS only. Clones, worktrees and commits run as the engineer against the mirror. Publish: root fetches the engineer's branch through `git upload-pack` run as the engineer (`ext::runuser ...`), so root never opens a repo or config the agent can write, then pushes `sha:refs/heads/<branch>` without force. When the owner's token is missing or GitHub refuses it, the step fails with a message saying the owner must sign in again or get access; checkpoints never fall back to another member's token. Proven in a throwaway Ubuntu 24.04 container (`test/vm/gitDocker.test.ts`, `VM_DOCKER=1`) with a hostile repo-local and global config and an agent-uid scanner of `/proc`.
- Usage probe (`vm/usage.sh`, section 8.5).
- Pause only from the backend when no live lease uses the VM. Resume calls `vm.start()` then waits for `node.status.online` and probe success.

### 8.3 Agent Relay
- One workspace per team (`AgentRelay.createWorkspace({ name: 'morrow-<teamId>' })`), key encrypted in `Team.relay`. Register `dispatcher` (type system) and one `human` identity per member lazily (`h-<login>`), tokens stored encrypted; never re-register an existing name (registration is create-only: an existing name fails with `name_conflict`, `strict` or not).
- Observer token with `includeDms: true`, read-only, rotated on member removal.
- Node per environment: name `n-<envShort>`, `AGENT_RELAY_NODE_HARNESSES` set to the CLIs that have a ready profile on that VM (rewrite env file + restart unit when profiles change), `AGENT_RELAY_NODE_MAX_AGENTS` = 8 per ready CLI (the per-profile ceiling), at most 16. It never follows a profile's `maxConcurrent`: the actor holds every lease to that, so changing it restarts nothing.
- Spawn: `messaging.placement.spawn({ capability: 'spawn:<cli>', node, confirm: true, input: { name, cli, task, channels: ['proj-<projectShort>'], worker_cwd: <absolute worktree path> } })` with the dispatcher token. For opencode the input also carries `harnessConfig: { runtime: 'pty', command: 'opencode', args: ['--agent', 'agent-relay'] }` (`spawnPlacementInput` in `relay/spawn.ts`): without `--agent` the broker writes an `opencode.json` holding the workspace key into the worktree. Task brief under 14 KB; long context goes into `.morrow/briefs/<workstream>.md` committed on the branch, with a pointer in the task text.
- **Node layout (who holds the workspace key).** The broker (agent-relay 14.0.0) gives every CLI it starts the workspace key: in four environment variables (`RELAY_API_KEY`, `RELAY_WORKSPACE_KEY`, `AGENT_RELAY_WORKSPACE_KEY`, `RELAY_WORKSPACES_JSON`), in the MCP config on the command line (Claude Code `--mcp-config`, Codex `--config mcp_servers.agent-relay.env.RELAY_API_KEY=...`) and in a worktree `opencode.json` for opencode. No broker option turns this off, and no released version changes it. With the key a worker could register as or take over any name (`dispatcher`, `h-<login>`, other workers) and read every channel. So `vm/configure-node.sh` splits the node into two Linux users:
  - The broker runs as `r<hex>` (same hex as the engineer's `u<hex>`), a system user with home `/var/lib/morrow/relay/r<hex>` (0700) holding its state: node token, local API key, worker logs. The unit pins the broker's project root to `relay-node` (`AGENT_RELAY_PROJECT`), so its state dir is always `relay-node/.agentworkforce/relay`; otherwise agent-relay picks the nearest dir holding Relay files, which moves. Its unit adds the engineer's group (`SupplementaryGroups`) only so it can reach the worktrees (`chmod g+x` on `~/work`, `.worktrees` and each worktree; never read or write).
  - The CLIs run as the engineer. The broker's `PATH` starts with `/opt/morrow/relay-shims`, whose `claude`, `codex` and `opencode` call `/opt/morrow/bin/relay-worker launch` (`vm/relay-worker.sh`). As `r<hex>` it removes the key from the arguments, then runs `sudo -n -u u<hex> relay-worker exec <cli> ...`. The sudo rule (`/etc/sudoers.d/morrow-relay-r<hex>`, checked with `visudo`) allows that one command as that one user, resets the environment to a fixed allowlist (agent name, agent token, base URL, terminal settings; never a key variable) and keeps the CLI on the broker's PTY (`!use_pty`, `!pam_session`). sudo stays as the CLI's parent on purpose: it holds the broker's real uid, so the broker can signal it and it passes signals on; a CLI exec'd in place would run purely as the engineer and the broker could not stop it on release. `exec` refuses to start if anything key-shaped is still in its environment or arguments, then runs the real CLI from the engineer's login `PATH`.
  - The MCP server the broker writes into each CLI's config is `relay-worker mcp` (`AGENT_RELAY_MCP_COMMAND`): `agent-relay mcp` with only the worker's own agent token. A literal `${RELAY_API_KEY}` placeholder stops it from falling back to a key file on disk. Messaging tools work; workspace-wide tools (`list_agents`, `add_agent`, `spawn`, `remove_agent`, `query_nodes`) do not, since they need the key. opencode gets the same server and the `agent-relay` agent through `OPENCODE_CONFIG_CONTENT`.
  - `/proc` is remounted with `hidepid=invisible` (plus an fstab line) and the unit has `ProtectProc=invisible`, so the engineer cannot read the broker's environment or its PTY processes' command lines. If the remount fails the step reports `procHidden: false` and the runtime logs `environment step warning` (`proc_not_hidden`); the unit's own hidden `/proc` still covers the workers. The unit drops `NoNewPrivileges`, because sudo is setuid.
  - golden-setup installs `lsof`, and `configure-node.sh` refuses to run without it. agent-relay checks a crashed broker's node claim (`~/.agentworkforce/relay/node-claims`) with `lsof`; without it the claim reads as held forever and the unit restarts into "already served by a live broker" for good. Both scripts also make `/opt/agent-relay` readable (`a+rX`): the installer leaves its binaries execute-only (0711), and Linux marks a process started from a binary its user cannot read as non-dumpable, which hides its `/proc/<pid>/fd` even from that user. agent-relay then cannot verify its own broker with `lsof` and refuses to start ("Could not persist a verified broker process identity") whenever it runs as a non-root user.
  - Migration: a node that ran as the engineer is stopped, its node token is copied into the broker's home and its id pinned (`/etc/agent-relay/node-id`, passed as `RELAY_NODE_ID`; the id is derived from the working directory, which moves). Its registration proof moves too: the broker proves to the engine that its name is its own with a key derived from its state file path (sha256 of `<project root>/.agentworkforce/relay/state-<node>.json`), and without the old one the engine refuses the name (409 `agent_identity_mismatch`). Migration finds the old project root (the dir whose `broker-<node>.lock` was written last), pins the old key in `/etc/agent-relay/identity-key` (0600 root) and passes it as `RELAY_AGENT_IDENTITY_KEY`, which the broker strips from worker environments and sudo drops again. Then every Relay file in the engineer's home is deleted. `nodeConfigHash` includes a digest of `configure-node.sh` and `relay-worker.sh`, so every node is re-laid-out on its next sync.
  - Proven by `test/vm/relay-node-docker.test.ts` (`VM_DOCKER=1`): Ubuntu 24.04 with systemd, Agent Relay from golden-setup's relay step, a real engine, and fake CLIs that search their environment, arguments, every visible process and readable file for the key, then post to a channel, send and receive DMs through the MCP server.
- Truth for "running": node `relay:live-agents:v1` contains the name, or `agent.status.active` seen. Truth for "gone": `agent.exited` with reason `deregistered` or `released`, or absence from live-agents on 3 reads of newer node heartbeats spanning 30 s, at least 60 s after the spawn, unless the worker's PTY log on the VM changed after the absence began. `agent.exited (missing_from_inventory)` is the engine's inference and is never proof on its own: under hosted Relay database pressure it fires for running workers, and node records lose the live-agents capability while online with a fresh heartbeat (that reads as unknown, not as an empty list). See `backend/src/integrations/relay/reconcile.ts`.

### 8.4 Terminals
- Owner private terminal: token TTL 15 min, `Cache-Control: no-store`, grant restricted to the engineer's Linux user. `EnvironmentRunner.mintTerminal` gives each environment its own Freestyle identity (stored on the environment, created on first mint, deleted on disconnect), so a token opens one VM only. Migration: the older user-wide identity (`User.freestyleIdentityId`) is never minted from again; each VM's first mint revokes its grant there, and disconnect and sign-out everywhere revoke it too. Browser uses `connectXterm` with `slug: 'main'`, shell `env TERM=xterm-256color bash -l`.
- Read-only inspect: Relay workers run in the broker's own PTYs, not Freestyle terminal sessions, so inspect streams the worker log tail instead. `POST /api/teams/:teamId/inspect/ticket` mints a single-use ticket bound to user + team + lease with purpose `inspect` (a `/realtime` ticket is refused). WS `/realtime/inspect/:leaseId` polls `readWorkerLogTail` every 1.5 s and sends only new bytes; client input is dropped; it closes when the lease ends, the member is removed, the user signs out everywhere, or policy turns inspect off.
- Worker logs live in the broker's home (`/var/lib/morrow/relay/r<hex>/relay-node/.agentworkforce/relay/team/worker-logs/`) and are read by `vm/logtail.sh` exec'd as the broker's user `r<hex>` (never root, never the engineer, who cannot read them). It opens the file once and checks the open handle: exact path, regular file, owned by that user, one link. Last 64 KB, read timeout 5 s. Needs a running VM; only live leases are read. Inspect streams this text verbatim to members, with credential-shaped tokens masked.

### 8.5 Plan usage (the team pool)
The pool meter shows how much of every member's plan is left, per CLI. Only percentages and reset times leave the VM: never a token, a token count or money.

Sources:
- **Probe** (`vm/usage.sh`, `exec` as the engineer's Linux user, `timeoutMs: 40000`, run by `ProfileService.refreshUsage`). Claude Code: `GET https://api.anthropic.com/api/oauth/usage` (the endpoint behind `/usage`, header `anthropic-beta: oauth-2025-04-20`) with the OAuth access token from `~/.claude/.credentials.json`. Codex: `account/rateLimits/read` over `codex app-server` stdio, which reads the plan's limits without running a model turn; when that fails, the `rate_limits` of the newest `token_count` event in the last 8 days of session rollouts (`~/.codex/sessions/**/rollout-*.jsonl`, observed at that event's own time). opencode bills the user's own provider keys and has no plan window: shown as "No plan limit".
- **Worker output** (monitor, section 9.3): Claude `rate_limit_event` stream-json, Codex `token_count.rate_limits`, and the TUI lines "You've used N% of your weekly limit", "You've hit your 5-hour limit", "Heads up, you have less than N% of your 5h limit left". Parsed in `orchestration/workerUsage.ts`; each printed line is recorded once per lease.

Cadence: probe reads ride the 60 s environment probe loop, which only runs for teams with a connected viewer or a live lease. Each environment is read at most once every 5 min plus up to 60 s of jitter, failures included (the next due time is set before the read). Only signed-in Claude and Codex profiles on a ready, running VM are read; a VM with none is skipped without an exec. Reads share a single flight per environment and never take the environment lock.

Credential handling on the VM: the script runs as the engineer, so it reads only that engineer's own login, which the CLI already uses there. The token is checked against a strict charset, never refreshed (refreshing rotates it and a lost race signs the CLI out), and skipped when expired or missing the `user:profile` scope. It reaches curl only as a config read from stdin (`-K -`), never argv or environment; `curl -q` ignores `~/.curlrc`, HTTPS only, TLS 1.2+, no redirects, 8 s timeout, response capped at 64 KB. The script prints only `{status, windows[{used, resetsAt}]}`. A Docker test (`test/vm/usage-docker.test.ts`, `VM_DOCKER=1`) runs it against fake curl and fake `codex app-server` and fails if the token shows up in argv, environment or output.

Storage and fan-out: the backend clamps percentages to 0-100, drops reset times that are invalid or more than 35 days out, and calls `recordProfileUsage`. The actor rejects readings from the future (beyond clock skew), ignores any not newer than the stored one, replaces windows for a probe reading and merges by window for a worker reading, and rewrites an unchanged reading at most every 5 min. Usage writes skip the idempotency ledger (the `observedAt` check makes them safe to repeat). The reading travels on the existing `workforce.view` frame, so every member sees it live and no one outside the team does; the browser never polls.

Freshness: a reading older than 30 min (`USAGE_STALE_MS`) is stale. The meter draws it dimmed, labels it "Stale", and leaves it out of the pool total. A window whose reset time has passed reads as full again.

Meter (`web/src/components/pool/`): one segment per CLI, grouped by member, filled with the headroom left in the binding window (the lower of 5-hour and weekly left). States: healthy, low (under 20 % left), limited (with its reset time), needs sign-in, offline, no plan limit, and no data yet (hatched). The headline is the mean headroom over CLIs with a current reading, limited ones counting as 0. Shown in the sidebar footer and under the composer; the popover lists member, CLI, each window's percent left and reset, and when it was read.

### 8.6 GitHub layer
Pull requests, branches and worktree commits inside Morrow, so a team never has to open github.com. Code: `backend/src/github/` (`service.ts` reads and writes, `pulls.ts` maps GitHub JSON to contracts, `cache.ts`, `sync.ts`, `events.ts`, `worktrees.ts`), routes in `http/routes/github.ts`, contracts in `packages/contracts/src/github.ts`, UI in `web/src/components/github/`.

- **Whose token.** Every read and write uses the signed-in member's own GitHub token, decrypted in memory for the call, so GitHub enforces their real permissions (a member without write access cannot merge, and GitHub says so). Tokens never reach the browser or an agent uid. A 401 or a missing scope comes back as `unauthenticated` with a "Reconnect GitHub" message; the UI links to sign-in.
- **Scope.** Only projects linked to the team: the route resolves `:projectId` from the team's own project list, so the repo name always comes from the team, never the request. Pull numbers match `^[1-9]\d{0,9}$`, comment ids are positive integers, every URL is `GITHUB_API_URL` + a path built from validated parts (no SSRF). Routes go through session, CSRF, membership (404 for outsiders) and the `github` bucket (30 burst, 1 per 2 s per user); comments, merges and commits are writes in that bucket.
- **Cache and rate limits.** `GithubCache` keeps the last answer per (user, URL) with its ETag and sends conditional requests, so an unchanged resource costs a free 304. It reads `x-ratelimit-*`: when a member's limit is spent it serves the last copy with `freshness.stale` and `rateLimitedUntil` instead of calling GitHub, and the UI says so. Outages also serve the last copy, marked stale. Bounded by entries and bytes.
- **Live updates.** `GithubSync` polls every 30 s for teams with someone connected. Per team it reads as a connected member (else a creator of a running task), lists each linked project's pull requests (up to 10 projects) and watches up to 10 pull requests that belong to running tasks: head SHA, checks and new comments. A change publishes `github.changed { projectId, pulls, list, at }` to the team. It carries no content: each browser refetches with its own token, so nobody sees what their own GitHub access would not show them. Writes made through Morrow publish the same frame at once.
- **Agents hear review comments.** New review comments, review bodies and conversation comments on a task's pull request go to `orchestration.comms.reviewComment(event)` (section 9.8), at most 20 per pull request per pass, oldest first. The first pass only records a baseline, so a restart never replays old comments.
- **Merge.** The UI offers only the methods the repo allows (`allow_squash_merge` and friends, visible to members with push access) and sends the head SHA it showed; GitHub refuses a merge if the branch moved (409), is not mergeable (405) or the method is not allowed (422). Each refusal maps to a plain message. Merge, close and reopen sit behind the member's own permission on GitHub; merge also asks for confirmation.
- **Commit and push from the web.** `worktrees.ts` runs `git.sh status` (as the user, read only) to list the worktree's changed files, conflicts and unpushed commits, and `checkpointWorktree` with conflict checking to commit everything and push the branch with the repo owner's token, author set to the member (`<id>+<login>@users.noreply.github.com`). Allowed for the task creator, owner and admins (same rule as cancel and retry). One commit per workstream at a time (409 otherwise). Refused with a reason when the worktree has merge conflicts, no agent has run there, the VM is paused or gone, or Freestyle is not configured (501, the UI shows it as unavailable).
- **Rendering.** Comment and description markdown is parsed by `web/src/components/github/markdown.ts` into a small tree and rendered as React elements: raw HTML is shown as text, links pass `safeHref` (http and https only, no credentials) and open with `noopener noreferrer nofollow`, images become links. Bodies over 20,000 characters are cut.

## 9. Orchestration

### 9.1 Planner
1. Gather context: repo tree (GitHub API, depth-limited), README excerpt, task prompt, acceptance criteria, ready profiles.
2. Run a headless planning call on a ready profile through its VM: `claude -p --output-format json` (or `codex exec --json`), 120 s timeout, with a strict JSON schema prompt. This spends the team's own subscription, which is the point of the product. The planner never takes a lease for this; it uses a short `planning` hold recorded on the profile.
3. Validate the JSON (zod). Enforce heuristics: 1 workstream for small changes, otherwise as many as the work needs, never above `maxAgents` (the smallest of `MAX_TASK_WORKSTREAMS` = 5, the slots of every profile that may take the task's work, and a "fewer agents" re-plan). Only workstreams that would edit the same files in parallel are merged; a test/integration stream gated on the others may overlap them. Every workstream gets a branch `morrow/<taskShort>/<role>` and file ownership globs.
4. Fallback when no profile is ready or the call fails: deterministic heuristic planner (single workstream, explicit "planner fallback" reason in the UI).
5. Output includes a human-readable rationale per workstream. Shown before Start.
6. Refine: `POST .../plan` with `feedback` (max 4 KB, untrusted, fenced in the prompt file, never in shell) re-plans the same task from the previous plan + original prompt + feedback. Only from `planned`; a request while another is queued gets a 409.
7. Headless CLIs run with `TZ=UTC` (Codex prints reset times in local time without a zone). Limit detection prefers structured fields (`claude -p` JSON `api_error`), regex as fallback; patterns and fixtures in `docs/research/cli-signals.md`.

### 9.2 Dispatcher (outbox)
The backend holds one actor socket per tracked team (`backend/src/orchestration/feed.ts`). It claims when a push says an item is due (`outboxSummary.nextDueAt <= now`) and at that time otherwise, plus a safety claim once a minute; without a live socket, or from an actor that does not emit the summary, it polls every 1 s while the team is hot and every 10 s otherwise. A claim: `claimOutbox` → perform side effect (Relay spawn/release, git checkpoint via exec, brief commit) with our idempotency (agent name derived from lease epoch, Relay `idempotencyKey` = outbox id) → `completeOutbox`. Errors back off exponentially (1 s → 60 s, max 8 attempts) then mark the lease `failed` and surface it. `spawn_unconfirmed` / timeouts go to reconcile, never blind retry. A claimed item the process cannot start (shutdown began while the claim was in flight, or no free slot) goes straight back as a retryable failure, so a deploy costs one attempt and a 1 s backoff instead of the visibility timeout (6 min for a spawn); if even that call fails, the visibility timeout brings it back.

### 9.3 Monitor
- Relay lifecycle → `recordSpawnStatus` / offline transitions.
- Every 20 s per running lease: read the tail of the worker log (`<node cwd>/.agentworkforce/relay/team/worker-logs/<agent>.log`) with `vm/logtail.sh` as the engineer (last 64 KB, section 8.4) and classify: usage/quota limit, auth expired, crash. The same tail feeds plan-usage readings (section 8.5). Patterns are versioned in `orchestration/classifier.ts` with tests from real CLI output samples. A detected limit calls `markProfileLimited(source: 'detected', until: parsed reset time or now + 60 min)`.
- Freestyle state poll → environment `vmState`, node expectations.

Workers never push. A worker posts `DONE <leaseId>` in the task thread when its workstream is complete; the backend commits the worktree as the engineer's Linux user and root pushes it from the mirror with the environment owner's token (section 8.2), then calls `completeWorkstream` with the SHA it pushed. If the owner's GitHub access is gone, nothing is pushed: the team channel gets a notice and the workstream stays open until the owner signs in again and the worker posts DONE again. Errors stored in task traces and outbox results are fixed safe strings; raw vendor text goes to server logs only.

Dead-lease rule (Relay engine bug: a crashed worker can leave its node's control link failing with no `agent.exited`): a running lease is treated as dead when it reads `unknown` more than 3 consecutive reconciles with a crash in its log, or its node is offline past 90 s. The runtime then calls `restartNode(teamId, envId)` (restarts the broker unit; at most once per 2 min per environment) and handoff proceeds.

### 9.4 Handoff
On a revoked lease with an incomplete workstream: checkpoint the dead worker's worktree (commit as its Linux user, push from the root-owned mirror with the environment owner's token, section 8.2), record the SHA, choose a replacement (prefer a running worker with slack on the same task only if its workstream is done; else best ready profile on another node by score), reserve a new lease (new epoch), write `.morrow/handoff/<workstream>.md` (requirements, decisions from the Relay thread, changed files, outstanding tests, last errors) on the branch, spawn the replacement with a short pointer brief. The replacement must post `ACK <leaseId>` in the task thread; the observer sees it (sender name must equal the lease's agent name) and calls `ackHandoff`.

### 9.5 Verifier
A task finishes only when: every workstream reports done with a SHA that exists on the remote (GitHub API), the integrator branch merges cleanly (GitHub compare / PR mergeable), and the test command (`project.testCommand`, detected from package.json or set by the user) exits 0 in a fresh worktree on a ready VM (`exec`, 5 min). Evidence is stored with the task and shown in the UI.

Tests run only on an environment that has a CLI profile allowed on the project (scopes `all` or the project's id), that is not offline, and whose environment is `ready`. Environments that already ran this task's workstreams go first. With none, the check fails with "no ready environment has a CLI allowed on this project". The test output can hold anything the suite prints, so it goes through `redactSecrets` (`runtime/inspect.ts`: Relay, GitHub, Anthropic and OpenAI token shapes, JWTs and named token fields) before the last 1,500 characters are kept, and it is only included when the team policy `allowInspect` is on; otherwise the check says the exit code and that the output is hidden.

**Merge conflicts.** By the time the verifier merges, every workstream has posted DONE and its lease is released, so a conflict gets its own worker (spec section 11):
- The verifier's merge (a workstream branch into `morrow/<taskShort>/integration` returning 409, or the pull request not mergeable into the default branch) records the conflicting branch, the workstreams already merged and still to merge, and the files changed on both sides (GitHub compare in both directions). It calls `resolveConflict` instead of `submitVerification`; the key includes the task's `updatedAt`.
- `resolveConflict` (only from `verifying`) adds or resets one workstream, `ws-resolver` (role `resolver`, branch = the integration branch, `dependsOn` = the workstreams on either side, its brief from `conflictBrief`), sets `resolving` and increments `resolutionAttempts`. The verification shows a pending "Conflict resolution" check. Trace: `task.conflict_detected`.
- The scheduler leases it like any pending workstream (scope, pool and cap rules), with the profiles that worked on either side pinned first. Trace: `task.resolver_reserved`. The brief names the integration branch, the conflicting branch and commit, the files, what each side was doing, and the exact steps: `git merge origin/<integration>`, `git merge --no-ff origin/<branch>`, resolve, commit, merge the remaining branches, run the tests. Never rebase, reset or force.
- The resolver's DONE is checkpointed with `CHECK_CONFLICTS=1` (`vm/git.sh`): unmerged paths are never committed, and nothing is pushed while a path is unmerged or carries leftover conflict markers against `origin/<integration>`. Then the team channel gets a notice naming the files and the worker keeps its lease. A clean commit is published like any checkpoint (fast-forward, never forced), `completeWorkstream` records it (`task.conflict_resolved`), and the task returns to `verifying`. The earlier branches are now ancestors of the integration branch, so their merges are no-ops.
- At most `WORKFORCE_LIMITS.conflictResolutions` (2) attempts. After that, or when a planned workstream already owns the integration branch, the task fails with a "Conflict resolution" check and a `task.conflict_gave_up` trace that say which branch, why, and that a retry gives 2 more attempts. A retry resets `resolutionAttempts`.
- The planner never emits the roles `integration` or `resolver` (renamed to `integrationtests` and `resolve`), so no planned branch collides with these.

**Retry** (`retryTask`, the task's creator or an owner or admin, the same rule as cancel; `failed` only; the HTTP check order is 404, then 403, then 409; the only transition out of `failed`). A failed task holds no live lease, so no fencing is needed beyond the status check and the idempotency key:
- every workstream `done`: `failed -> verifying`, old evidence cleared. The backend drops the verifier's in-memory backoff and runs it at once. The `submitVerification` key includes the task's `updatedAt`, so a re-run with identical evidence is applied, not answered from the ledger.
- otherwise: unfinished workstreams go back to `pending` (branch, last checkpoint and old lease id kept, so old epochs stay fenced out), done ones stay, and the task re-enters the started states (`planned`, derived to `running` when something is done). The backend reserves workers for the ready workstreams within the policy cap at once; the rest come from the scheduler. New leases get fresh epochs. The scheduler's failed-start and handoff budgets count only leases created after the last retry.
Both record a `task.retried` trace entry naming who retried.

### 9.6 Reconcilers
With a live socket: the scheduling pass (handoffs, reservations, verification) runs when the pushed view changes, at most every 5 s, reading the pushed view; `TeamWorkforce.reconcile(now)` (the actor's deadline sweep, which its own alarm also runs) and a full pass run once a minute. Workers are told about changes (section 9.8) when the view moved since the last clean pass, or once a minute. Without a live socket: everything every 15 s, as before. Relay spawn reconcile for `spawning` leases older than 120 s; environment phase reconcile. All idempotent.

`getView` reads go to the pushed copy only when it is current: the socket is open and holds a snapshot from this connection, and no write to that team through this process is in flight or finished less than 1 s ago (a write's state update is published before its response, but on a different path). Otherwise the read goes to the actor. Measured for one team with two running workers (`backend/test/orchestration/callRate.test.ts`): 108 actor calls a minute while hot and 54 idle before, 14 after either way; 6 of those are the per-worker liveness reads every 20 s (`getLease`). The worker's profile comes from the pass's view instead of a `getProfile` call.

**Restarts.** Which teams to resume comes from the `TeamDirectory` actor (one instance, id `teams`, `actors/src/lib/directory.ts`): the backend notes a team as active (`noteWork`, which bumps a generation) before it creates or retries a task, and reports it idle (`noteIdle` with the generation it last read) when the team has had nothing to do for 10 minutes; work noted in between, by any replica, keeps it active. At boot and every 5 minutes the backend lists the active teams and tracks them. The control plane's actor inventory is read too, as a hint only: it is a per-process, in-memory list that a Terse restart empties and that forgets idle actors. A busy team found only by the hint, or whose note failed at task create (the create goes ahead after 5 s), is written to the directory on its next pass. Backend restart: the directory list brings every unfinished team back, and claims, sweeps and passes resume within a minute. Terse restart: actor state and SQLite survive; the dev server loses pending alarms, which the once-a-minute `reconcile(now)` restores, and backend sockets reconnect (with a fresh snapshot) on their own.

### 9.7 Parallel cap and placement
Team policy `maxParallelPerTask` caps workers per task at once: the picks at start and every scheduler pass (active plus handoff workstreams hold a slot), and a compare's harness count at create. It never shrinks a plan. Start takes the starting workstreams that have a free slot now (a compare: all of its attempts or none) and the rest are queued: the scheduler gives each the next free slot. Read live, so a change applies on the next pass.

Which profile takes a workstream (`backend/src/orchestration/scoring.ts`): hard rules first (ready or busy, signed in, in scope, a free slot, VM ready, the attempt's harness), then a score (pins, healthy auth, node online, free slots, spreading one task over machines). A task stores `mode` (`auto` or `manual`) and `pins` (at most 5 of the team's profiles; tasks stored before this read as auto with no pins). In auto, pins are only a preference. In manual, only pins ever take the task's work: the actor refuses any other profile with `not_pinned` in `reserveWorkers` (start, scheduler, resolver, compare attempts), `requestHandoff`, `beginPlanning` and `delegate`, and the backend's start, retry, scheduler and planner offer only the pins (`placementPool`). The scheduler places the ready workstreams that fit and leaves the rest pending; in manual, one with no free pin gets a `worker.waiting` trace entry written by the actor (`noteWaiting`, once per wait), and nothing falls back to an unpinned profile. Mode and pins change only before any worker is placed (`setTaskWorkforce`, else `task_started`), and stay out of `TaskView` and `TaskDetail`: the backend reads them from `getTask`. Details: `docs/multi-harness.md`, "Manual mode".

### 9.8 Agent communication
Code: `orchestration/comms.ts` (roster, updates, STATUS, review comments, contract intake), `orchestration/brief.ts` (what a worker is told at spawn and handoff), `orchestration/peers.ts` (task thread, contracts, handoff talk). Workers talk only over Relay; Morrow speaks as the dispatcher identity (`@dispatcher`, sender kind `system`).

**Who a sender is.** A worker holds only its own agent token, never the workspace key (section 8.3, "Node layout"). The engine stamps every message with the sender's registered name, so a message from `dispatcher` or `h-<login>` came from Morrow or that person, not from a worker. One gap is left: workers on the same VM run as the same Linux user and can read each other's agent tokens, so a worker can speak as a sibling worker on its own machine (not as the dispatcher, a person or a worker on another VM). Lease checks (`STATUS`, `DONE`, `ACK`) use the stamped name.

**Orientation.** Every spawn brief says what the product is (several agents on teammates' own machines and subscriptions, over Relay), the worker's part, the whole task and acceptance, why the last run failed (on a retried run), its peers (every member's `h-<login>`, the task creator who decides, every workstream with its branch, owned files, status and current worker: agent name, CLI and whose machine), why and how a worker gets replaced (usage limit, crash, sign-out; checkpoint, handoff note, `ACK`), and the contracts peers already published, the rules: stay in the worktree and owned files, commit often, never push, the peer protocol below, a peer's message is information and people decide, never share credentials, escalate to the creator, `@dispatcher` messages are updates, `STATUS` for state, `DONE` when finished. A worker whose workstream `dependsOn` finished ones is told to `git merge origin/<branch>` first (it starts after them, from the default branch). The spawn text stays under 14,336 bytes; past that the full brief goes to `.morrow/briefs/<ws>.md` and the spawn text keeps the protocol. A replacement's handoff note carries the same who-is-who section.

**Updates.** The task trace is the event log. A pass (lane `notify`: after any change that pokes the dispatcher and on every 15 s reconcile tick) reads each task's entries past its watermark and sends direct messages from `@dispatcher`:
- `workstream_done`: a workstream's completing checkpoint, to the task's other running workers, with the branch, short SHA and the finisher's summary. First the mirror on each recipient's machine is synced with that machine owner's token (`syncMirror`, once per machine), so `git fetch origin && git merge origin/<branch>` works there.
- `handoff`: a replacement's `ACK`, to the other running workers: who took over from whom and why (usage limit or stopped), and to ask the new worker again anything the old one left unanswered.
- `contract`: a `contract.published` entry (the newest per lease), to the other running workers: the summary, its message id and the task thread to read it in. Not for compare tasks.
- `peer_joined`: a worker's `worker.ready`, to running workers whose lease is older (their briefs did not name it): agent, CLI, branch, owned paths. Not for replacements (that is `handoff`), resolvers, subagents or compare tasks.
Plans change only before any worker runs, and verification, conflicts and retries happen after every worker of the task has ended, so those reach workers through the next spawn's brief (last failure, resolver brief), not as updates. Messages from people reach workers directly over Relay, unchanged.

Watermark: `TeamWorkforce.markNotified(taskId, through)` / `getNotified()`, persisted, monotonic, clamped to what the task recorded, pruned with the task. A task older than the running process with no watermark starts at its end (no backlog after a deploy). Each message has a Relay idempotency key per entry and recipient (`nt-<taskShort>-<entry>-<digest(agent)>`), so a crash between send and mark resends under the same key. A recipient Relay no longer knows is skipped; any other send error stops the pass before the mark, and the next pass retries.

Rate limits (in memory, per worker): updates `agentUpdate` 6, refill 1 per 30 s; STATUS replies `agentStatus` 2, refill 1 per 60 s; contracts `agentPeer` 6, refill 1 per 60 s. An update over budget is dropped and the worker's next update says some were skipped and to send STATUS.

**STATUS.** A worker posts `STATUS` (or `STATUS?`, optionally after `@dispatcher`) alone on the first line, ideally as a DM to `@dispatcher`. Only a `w-` sender with a live lease gets an answer (the engine stamps the sender; text never names who to answer), covering that lease's task only: task status, creator, each workstream with status, finished summary and worker, the last verification failure, the newest three trace entries, the people. Keyed by the request's message id (`st-<digest>`), so a replayed request never answers twice.

**Review comments.** The GitHub layer calls `orchestration.comms.reviewComment(event)` once per new pull request review comment (`ReviewCommentEvent`: teamId, taskId, commentId, author login, path, line, body, https url; zod-validated). It goes to the running workers whose ownership globs match the path (`Bun.Glob`; a bad planner glob matches nothing), else to every running worker of the task. Key `nt-<taskShort>-rc<digest(commentId)>-<digest(agent)>`.

**Subagents.** A worker can start another CLI on its own machine as a subagent (`docs/subagents.md`). Requests are DMs to `@dispatcher` whose first line is `SUBAGENT_OPTIONS`, `DELEGATE`, `TASK_STATUS`, `TASK_CANCEL` or, from the subagent, `RESULT`; the `morrow-agent` MCP server on the VM sends the same lines with the worker's own Relay token, and the brief documents the plain form. `orchestration/subagents.ts` parses and phrases them; `Comms.subagent` resolves the engine-stamped sender to its live lease, rate limits on intake (`agentDelegate` 8, refill 1 per 15 s), and answers once by DM (notice `subagent`, key `sa-<digest>`) with a machine-read `[morrow ...]` last line. A subagent's `RESULT` holds back its exit like `DONE`. When a subagent ends on its own (a result, or it died), the `subagent.finished` trace entry drives a `subagent_done` DM to its parent through the watermarked update pass, not rate limited. Subagents never get task-wide updates. The dispatcher spawns a subagent in its parent's worktree path without touching it, with `subagentBrief()`: the request quoted under a fixed header, then the rules (read only for review and research, no commits, pushes or further delegation, finish with `report_result` or `RESULT`).

**Peers.** Workers coordinate in one task thread instead of the whole channel:
- Task thread: the first spawn of a task posts a kickoff in the project channel as the dispatcher (notice `kickoff`, Relay key `kick-<digest(taskId)>`; spawns racing in one process share one post) and stores its id on the task (`setTaskThread`, first write wins; `TaskDetail.threadId`, not in `TaskView`). Briefs name it and say to read it with `get_message_thread` on start and to post with `reply_to_thread`. If the post or the store fails, the worker is pointed at the channel and the next spawn tries again.
- Engine behavior this is built around (engine 12.2.1): a thread reply reaches every unmuted member of the channel, so other tasks' workers see it too; mentions only matter to muted members. The brief says to act on messages that @mention you or carry a contract you build on and ignore the rest, to ask a peer with `@<agent> <question>` and end the turn (the answer wakes it), to answer mentions first, and to ack with `add_reaction` (reactions reach the node as ack-only and wake no one).
- Contracts: `CONTRACT <leaseId> <summary>` on the first line, details below, before building something a peer calls or imports. `Monitor` routes it (channel or thread only, not a DM) to `Comms.contract`: the engine-stamped sender must be the lease's own live worker and not a subagent, rate limited, then `recordContract(leaseId, epoch, summary, messageId)` (fenced; refused once the workstream is done; same message is a no-op) stores the newest summary on the workstream and traces `contract.published`. The body (masked, 2,000 chars) stays in Relay, cached in memory and read back by message id as the dispatcher, only when the message is still from the publisher. New spawn briefs and handoff notes list every peer contract as quoted agent text.
- Handoff talk: `Monitor` keeps messages that mention a worker or person (300, in memory). A handoff note adds the questions peers asked the stopped worker that it never answered (no later message from it mentions the asker), what peers said to it (10 each, from the thread and the log), and the task's contracts; the replacement's spawn text says to read the thread and answer those first.

**Talk.** Workers are told to talk a lot, and Morrow keeps them at it (`orchestration/activity.ts`):
- Crew: a task whose plan has one workstream (a single-topic task like "Improve the SEO", or the planner fallback) gets partner workstreams so its builder has peers: `review` (pushes back on the plan, answers questions, does lookups, reviews the diff before DONE) and then `research` (finds what the change needs, audits the result). 3 workers when 3 or more slots are free, 2 when 2 are (`crewTarget`), never above the plan's ceiling or a "fewer agents" request. Partners own only `.morrow/<role>/**` and depend on nothing, so they never conflict at merge. When every builder is done, the `workstream_done` message tells each partner to post a final note and `DONE` with its own lease id. A plan the planner split already has peers and is left as it is. The orchestration option `partners` (on by default) turns this off; tests of one worker's lifecycle use that.
- Harness mix: placement (`choosePicks`) subtracts 25 points per worker of the same CLI the task already has or was just given (`cliUse`, from `taskCliUse`), which outweighs free slots and machine spread but not a pin or a replacement's own CLI. Claude Code 4 free + Codex 4 free gives a 3-worker crew on both. A single-harness team still gets its crew on that harness; `maxConcurrent` still caps every profile.
- Talk protocol in every brief (and in the short spawn text): the roster names each worker's harness ("Worker w-...-api-e2 (Codex on linus's machine)"); first actions in the first 2 minutes (read the thread, post a plan and @mention each peer, a partner greets the builder with a question, answer what is addressed to you); post at start, on claiming or finishing a piece, on an interface change (CONTRACT), with test results, when blocked and before DONE; ask peers for help (second opinion, diff review before DONE, lookups, unblocking); reply within a minute; ask before touching a peer's area; Slack tone with examples. The exact posting call is spelled out per CLI: `mcp__agent-relay__reply_to_thread` (Claude Code), `agent-relay_reply_to_thread` (opencode); other CLIs get the bare tool name and a hint that it comes from the `agent-relay` MCP server.
- Nudges (monitor watch pass, per running lease, only while another worker of the task runs, never subagents): a worker whose log keeps changing but who posted nothing in a channel or thread for 90 s gets a DM from the dispatcher (notice `nudge`), again after 3 more minutes, then every 6, at most 5 per lease per process; a post starts the schedule over. Never while its newest post asked a person (`h-`) who has not posted since. A peer's question that @mentions it and has gone 60 s without any post from it gets one reminder per question (key `ndq-<digest(lease|epoch|message id)>`), idle or not, at most 10 per lease. Last-post times come from the observer stream; after a restart the task thread is read once (an unreadable thread holds the nudge). Quiet nudge keys are `ndg-<digest(lease|epoch|last post time|nudge number)>`, so a restarted backend that sees the same silence sends the same Relay message. The text names peers only by engine-stamped name, never quotes agent text.
- Thread lines (notice `activity`, `to: []`, from the dispatcher, rate limited 8 per task then 1 per 30 s): from the trace in the update pass, `<agent> finished "<title>" (<role>) and pushed <sha> on <branch>` and `<agent> hit its plan's usage limit and stopped ... do not wait on <agent>` (key `ev-<taskShort>-<entry>`); from the worker's log tail, `<agent> ran the tests (<runner>): N passed, M failed` for bun, jest, vitest, pytest and cargo summary lines (counts only, key `ts-<digest(lease|epoch|line)>`). Only while another worker of the task runs: every line reaches every worker in the channel.
- `peer_joined` now asks the earlier workers to greet the newcomer in the thread; `handoff` asks them to send the replacement one line on where their work meets its, and the replacement announces itself after its ACK.

**Untrusted text.** Everything quoted to a worker (summaries, titles, trace lines, review bodies, paths) is flattened to one line, clipped and passed through `redactSecrets` first. Updates never carry tokens, env or log tails.

**Mission control.** Each update's Relay `metadata.morrow = { v: 1, kind, taskId, to }` (`RelayNotice` in contracts). The engine keeps metadata on channel posts and history but drops it from `dm.received` and `thread.reply` events, so the backend also remembers the notice of each text it sends (bounded, in memory) and attaches it when the event arrives. Only messages from the dispatcher identity get a notice, and a notice is display only. The timeline shows notices as their own rows (label per kind, who was told, the text without the `@worker` prefix, long replies folded), a worker's `STATUS` request as a status line and a `CONTRACT` as a contract card; the task view includes notices naming the task or reaching its workers and every reply in the task thread. Reactions and read receipts arrive on the observer stream and go to the browser as `relay.mark` frames (display only, never to orchestration); history messages carry reaction groups, a read count and stored attachment metadata (id, name, type, size; no links). A browser loads a task thread's older replies with the `relay.thread` client frame (answered as `relay.history` with `thread`).

**Relay Actions are not used yet.** Checked against engine 11.1.0 and `agent-relay` 14.0.0: actions register (upsert) and dispatch, the engine stamps the real `callerName` (read it from `getInvocation` or the observer stream; the handler's own WebSocket event reported a wrong caller), and only the handler can complete an invocation. But the engine does not validate input against `inputSchema`, `commands.list()` returned nothing after a register, and the stdio MCP server that 14.0.0 gives workers (`agent-relay mcp`, which the broker configures for the Claude Code, Codex and opencode harnesses) never registers `list_actions`, `invoke_action` or per-action tools; the `agent-relay capabilities` CLI only registers, lists and deletes. So no worker on our VMs can call an action, and a `morrow.*` action handler would be dead code. The text protocol (`DONE`, `ACK`, `STATUS`) stays, checked against the engine-stamped sender and the live lease. When a pinned version exposes actions to workers, `morrow.report_done`, `morrow.handoff_ack` and `morrow.task_status` map one to one onto these handlers.

## 10. Security model (honest boundaries)

- Vendor keys only on the backend. Secrets in Terse are AES-256-GCM encrypted with `DATA_ENCRYPTION_KEY` before they reach an actor.
- Relay workspace = trust boundary. Teams are isolated from each other. Inside a team, only the backend and each VM's broker hold the workspace key. The broker runs as its own Linux user (`r<hex>`) and starts each coding CLI as the engineer through a one-command sudo rule that drops the key; `/proc` hides the broker's processes (section 8.3, "Node layout"). So a worker, which runs with permission-bypass flags, has only its own agent token: it can message, but it cannot register or take over `dispatcher`, a person's `h-<login>` or a worker on another VM, and it cannot use workspace-wide tools. It can still read the agent tokens of other workers on the same VM (same Linux user) and speak as them. Members of one team are not isolated from each other's agents in that sense. Documented in the UI's security page.
- Provider logins stay in each engineer's Linux home on their VM. The platform never reads them. Our Freestyle key could technically read them (root); policy forbids it, code never does it, and no backend code path reads them. Two VM-side reads exist, both as the engineer's own Linux user: the health probe checks existence and CLI status output, and the usage probe (section 8.5) uses the Claude OAuth access token on the VM to read that login's own plan usage and reads Codex rollout rate-limit events. Only percentages and reset times come back; the token never leaves the VM, never enters argv or environment, and is never refreshed.
- Agent message text is untrusted input. Never interpolate it into shell commands; all exec uses `env` for values.
- GitHub tokens never reach an engineer's process: only root git on the VM uses them, from a root-only file, with every repo-local and global git config the agent controls ignored (section 8.2). A VM only ever gets its owner's token.
- Removing a member or a sign-out everywhere cuts that person's sockets and terminal access at once; removal also deletes their VMs in the team (section 4). Anything already read from those VMs before removal (for example the workspace key below) cannot be taken back.
- The Relay workspace key cannot be rotated today. The SDK (`@agent-relay/sdk` 14.0.0) has no rotate method. The engine (11.1.0) has `POST /v1/workspace/rotate-key` (`grace_seconds` 0 to 3600), but it is off unless the deployment sets `allowWorkspaceKeyRotation`, which has no CLI flag or env var; a call returns 403 `workspace_key_rotation_disabled` ("rotate through the managing control plane"). The hosted service was not tested (no key). Today the key on a VM is in `node.env` (root only) and in the broker's environment (the broker's own user), neither readable by the engineer or their agents. VMs set up before the broker had its own user gave the key to every worker, so a member or agent from that time may have it; they keep workspace access until the team is recreated.
- Terminal identity tokens: 15 min, single VM, single Linux user, never logged, never in localStorage. CSP on the web app: static headers from `web/src/lib/security-headers.ts` (no nonces, because nonces need per-request rendering and break Partial Prerendering; the App Router's inline RSC payload scripts mean `script-src` keeps `'unsafe-inline'`, no eval in production, no third-party script origins). Also nosniff, strict-origin-when-cross-origin referrer, camera/mic/geolocation off, X-Frame-Options DENY, HSTS in production.
- Input validation at every boundary (HTTP, actor methods, realtime messages).

## 13. Known limits (documented, not hidden)

- Relay engine bug (11.1 and 12.2): a crashed worker CLI can leave its node unusable until the broker restarts. Mitigated by the dead-lease rule and `restartNode` (section 9).
- opencode has no status command; "signed in" means a non-empty credential file, so an expired login reads as signed in until a real call fails.
- No "about to sign out" warning. A Claude `/login` and a Codex login hold a short access token the CLI renews by itself (so `usage.sh` reporting `expired` is routine) plus a refresh token whose lifetime the vendors do not document; a warning off the credential file's age would rest on a guessed number. Morrow reacts to the real thing instead: the probe's status command, the classifier's sign-in patterns in worker output, and the profile going to `auth_required` ("Signed out" / "Auth needed" in the UI, no new work placed on it). `TODO(saam):` offer `claude setup-token` as an opt-in login? Anthropic documents it as a one-year token with nothing to refresh, so its expiry is known and could be warned about exactly. It is read from `CLAUDE_CODE_OAUTH_TOKEN`, though: an environment variable is inherited by every child a worker starts (tool subprocesses, scripts that dump `env` into logs), where the credential file is only read by the CLI. Recommendation: not now; revisit once workers run under their own uid (section 9.8).
- The Relay workspace key cannot be rotated after a member leaves (section 10). Recreating the team is the only full cut.
- Workers on the same VM share the engineer's Linux user, so one can read another's agent token and speak as it (section 9.8). Workers cannot use the workspace-wide MCP tools (`list_agents`, `add_agent`, `spawn`, `remove_agent`, `query_nodes`); Morrow does not rely on them. The fix for both is upstream: Relay scoped worker credentials (relay issues #1903, #1379, #1570).
- A member removed mid-task loses the work their workers did after the last pushed checkpoint; replacements continue from that checkpoint.
- A conflict resolver whose workers keep failing to start (3) or stopping (8 handoffs) stops being scheduled like any workstream; the task stays `resolving` until someone cancels it.
- Handoff notes take "decisions" from in-memory Relay history; a backend restart loses that section (requirements, files, tests and errors are rebuilt from git and state).

- GitHub layer: comments posted while the backend is down are not sent to agents (the next pass sets a new baseline). The pull request view shows the first 100 files, reviews, review comments and conversation comments, and the list shows the 50 newest; the rest are linked on GitHub. Live updates come from polling (30 s), not webhooks. A comment is at most 60,000 characters, a commit message 2,000.
- Single backend instance (in-memory rate limits, tickets, hub). Horizontal scale needs a shared store for tickets/rate limits; actors already scale per team.
- Production runs on Terse Cloud: `terse deploy` from `actors/`, and the backend connects with `TERSE_ACTOR_URL` and `TERSE_API_KEY` (deploy/README.md). Local development runs `durable-actors dev` beside the backend, which keeps alarms in memory (lost on restart, restored by the backend's `reconcile` sweep) and resets its actor inventory on restart (the team directory covers it).
- The backend runs on one Mac mini behind Tailscale Funnel, and the web app on Vercel (deploy/README.md). The mini is a single point of failure: a power cut, network outage or macOS update takes the product offline until it is back. No state is lost, since it all lives in Terse. The backend hostname is a `*.ts.net` name; a custom `api.` subdomain needs Cloudflare Tunnel or port forwarding instead of Funnel.
- Limit detection is heuristic from CLI output. The pool meter shows plan usage as percent of each window and its reset time, never a token count or money.
- The Claude usage endpoint is the one Claude Code's `/usage` uses; it is not a documented public API and may change. The probe then reports "unavailable" and the meter falls back to worker readings and limit detection. Codex `app-server` method names track the CLI version on the VM; the rollout fallback covers a mismatch.

## 14. Observability

- Structured JSON logs (`lib/logger.ts`) with `reqId`, `userId`, `teamId`, `taskId`, `leaseId`, `epoch` fields. No secrets, no tokens, no message bodies at info level.
- `/readyz` answers up/down only; each call logs `readiness` with Terse latency and realtime counts. Background loops log a heartbeat each minute with counts (claimed, failed, reconciled).
- Every task has a decision trace (planner rationale, reservations, handoffs, verification), stored in TeamWorkforce and shown in the UI.

## 15. Testing

- Relay engine/broker suites run only with `RELAY_E2E=1` (they download an engine and start brokers).
- `actors/`: `bun test` against a real `durable-actors dev` (started by the test script on a random port with a temp data dir): concurrency races, rollback, fencing, idempotency, reconcile, validation rejections.
- `backend/`: unit tests (crypto, session, classifier, planner validation, outbox backoff); integration tests against real local Terse; Freestyle via a local mock server that mirrors the SDK routes; Relay against a real self-hosted `relaycast-engine` + `agent-relay node up` broker with a fake harness (as verified in research).
- `web/`: component tests for composer, keymap, radar; browser QA with `/qa` on every route.
- Live tests (real Freestyle/Relay/GitHub) gated on env keys, skipped otherwise, reported as skipped, never as passed.
